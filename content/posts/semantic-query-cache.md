Every AI agent that touches the outside world pays a repeated tax: the cost of re-fetching information it has already retrieved. Exact-match caching, the standard answer, fails almost entirely for AI-generated queries because identical intent routinely produces distinct query strings. This post describes a unified semantic cache backed by Qdrant that handles both web search and SQL queries under a shared collection schema, with differentiated invalidation strategies appropriate to each workload. I focus on the implementation details: the Qdrant collection design, topic-aware TTL via payload filtering on the `topic_tag` field, and surgical cache invalidation for SQL via the `tables_touched` payload field. The post assumes familiarity with vector databases and basic SQL.

## Why Exact-Match Caching Fails

Consider two queries generated by a research agent thirty minutes apart:

```
Query 1: "transformer attention mechanism explained"
Query 2: "how does self-attention work in transformers"
```

An exact-match cache (Redis, Memcached) sees two distinct keys and dispatches two API calls. The results are nearly identical. The second call accomplished nothing.

The same failure mode appears in SQL. A BI tool generates these two queries against the same schema on the same day:

```sql
-- Query 1
SELECT region, SUM(revenue) FROM orders
WHERE quarter = 'Q3-2025' GROUP BY region;

-- Query 2
SELECT territory AS region, SUM(sales_amount) AS revenue
FROM transactions WHERE fiscal_quarter = 'Q3-2025'
GROUP BY territory;
```

If `orders` and `transactions` are views over the same underlying fact table, both queries return the same data. An exact-match cache misses entirely on the second. A semantic cache recognizes near-identical intent and returns the cached result.

**GPTCache** ([Bang et al. 2023](https://arxiv.org/abs/2306.02779)) established the semantic caching pattern for LLM completions: embed the user prompt, search for similar cached prompts, return the cached completion when similarity exceeds a threshold. The cache key is the *embedding* of the query, not the query string itself.

GPTCache targets single-turn, stateless completions with no notion of freshness. Query caching for agents is harder: results expire, data sources change, and a stale cache hit for a SQL query returns silently wrong data. I want to extend the GPTCache pattern to handle these properties. Qdrant is the right backing store because its payload filtering is exactly the mechanism needed for topic-aware TTL and table-dependency invalidation: filtered ANN search lets the cache discriminate by topic category and table membership at query time, not just by vector similarity.

## Web Search vs. SQL: Two Different Problems

Before committing to a schema, it is worth being precise about how the two workloads differ, because the differences drive the most important design decisions.

**Web search** results exhibit *temporal staleness* but *semantic forgiveness*. A cached result for "latest LLM benchmarks" from yesterday is probably still useful today; a result from six months ago is not. The staleness threshold is topic-specific: breaking news expires in hours, research papers in days, reference documentation in weeks. Semantic forgiveness means that a cache hit at cosine similarity 0.91 is usually acceptable. Two differently-worded questions about the same topic will accept approximately the same search results.

**SQL** results exhibit *data staleness* and *semantic strictness*. A cached result becomes invalid not when time passes but when the underlying table is modified. Two queries with cosine similarity 0.91 may return numerically different answers if they apply different filters or join different tables. A false positive cache hit for SQL produces silently wrong data, which is worse than a cache miss.

These two properties drive the main architectural differences:

| Property             | Web search                  | SQL                         |
|----------------------|-----------------------------|-----------------------------|
| Cache hit threshold  | cosine > 0.92               | cosine > 0.97               |
| Invalidation trigger | Time (TTL per `topic_tag`)  | Data change (per table)     |
| False positive cost  | Minor relevance loss        | Silent wrong answer         |
| Result storage       | Compressed result list      | Pointer to result store     |
| Frequency signal     | Useful for TTL extension    | Useful for pre-warming      |

Both workloads share the same Qdrant collection. The routing logic and invalidation strategies diverge.

## The Qdrant Collection Schema

The cache lives in a single Qdrant collection called `query_cache`. Each cached query is one point, consisting of a named vector and a structured payload. The choice to keep both workloads in one collection rather than two is deliberate: it simplifies the infrastructure, and Qdrant's payload filtering is expressive enough to isolate query types at search time.

### Collection Creation and Named Vector

```python
from qdrant_client import QdrantClient
from qdrant_client.models import VectorParams, Distance

client = QdrantClient(url="http://localhost:6333")

client.create_collection(
    collection_name="query_cache",
    vectors_config={
        "query_embedding": VectorParams(size=1536, distance=Distance.COSINE),
    },
)
```

The single named vector `query_embedding` carries the embedding of the natural language query for web entries, or the embedding of the normalized SQL string for SQL entries. Using a named vector rather than the default unnamed field is a forward-compatibility choice: it lets you add a second vector (`sql_embedding`) to the same point later without migrating the collection, as covered in the SQL section.

### Payload Fields

```python
from qdrant_client.models import PointStruct
import hashlib, time

def make_cache_point(
    entry_id: str,
    query_text: str,
    query_emb: list[float],
    result: object,
    topic_tag: str,           # web: "breaking_news"|"research"|"reference"|"evergreen"
    tables_touched: list[str],# sql: tables read by this query; empty list for web
    ttl_seconds: int,
) -> PointStruct:
    result_json = serialize(result)
    result_hash = hashlib.sha256(result_json.encode()).hexdigest()
    now = int(time.time())

    return PointStruct(
        id=entry_id,
        vector={"query_embedding": query_emb},
        payload={
            "query_text":     query_text,
            "result_hash":    result_hash,
            "topic_tag":      topic_tag,
            "tables_touched": tables_touched,
            "created_at":     now,
            "ttl":            ttl_seconds,
            "hit_count":      0,
            "last_accessed":  now,
            "result_pointer": store_result(result),   # S3 / Redis key
            "stale":          False,
        },
    )
```

A few field-level decisions are worth explaining:

- `query_text`: the original natural language query or the normalized SQL string. Stored for debugging and pre-warming.
- `result_hash`: SHA-256 of the serialized result. Used during pre-warming to skip the result write when the underlying data has not changed.
- `topic_tag`: the payload field on which Qdrant's filter applies topic-aware TTL. Every web search lookup filters on this field. Possible values: `breaking_news`, `research`, `reference`, `evergreen`.
- `tables_touched`: keyword array listing the tables read by a SQL query. Every CDC-driven invalidation filters on this field. A point with `tables_touched: ["orders", "regions"]` is invalidated by a write to `orders` or a write to `regions`.
- `created_at` and `ttl`: stored together so that `created_at + ttl` gives the expiry Unix timestamp. The `ttl` field is set at write time from the per-topic TTL table.
- `result_pointer`: actual query results are not stored in Qdrant. Result sets can be millions of rows. Qdrant holds only the metadata and embedding; the result lives in S3, Redis, or local disk. This field is the key returned on a cache hit.
- `stale`: a flag set to `True` by invalidation jobs. Every cache lookup adds `stale: False` to its filter, excluding invalidated entries without deleting them (they are retained for analytics).

### Payload Index Configuration

Payload filters are only efficient if the relevant fields are indexed. Without indexes, a filter on `topic_tag` or `tables_touched` degrades to a full collection scan. Create indexes on every field used in filter conditions:

```python
from qdrant_client.models import PayloadSchemaType

for field, schema in [
    ("topic_tag",      PayloadSchemaType.KEYWORD),
    ("tables_touched", PayloadSchemaType.KEYWORD),
    ("stale",          PayloadSchemaType.BOOL),
    ("created_at",     PayloadSchemaType.INTEGER),
    ("hit_count",      PayloadSchemaType.INTEGER),
    ("last_accessed",  PayloadSchemaType.INTEGER),
]:
    client.create_payload_index(
        collection_name="query_cache",
        field_name=field,
        field_schema=schema,
    )
```

With HNSW indexing for the vector dimension and payload indexes for the filter dimensions, Qdrant executes the combined vector-plus-filter query efficiently. HNSW retrieves the top ANN candidates; the payload filter prunes them before final scoring. This is the core architectural reason Qdrant is appropriate for this workload: a simpler ANN library without filtered search would require post-filtering in application code, which is both slower and less precise for small collection sizes where post-filtering can exhaust the candidate set.

## Web Search Caching: Topic-Aware TTL via Payload Filtering

The key insight for web search caching is that TTL should be a function of the query's topic, not a single global value. A query classified as `breaking_news` should expire in one hour. A query about mathematical foundations should be valid for thirty days. Qdrant's payload filtering makes per-topic expiry efficient: every search passes a filter on `topic_tag` and `created_at`, so only entries of the correct topic category and within the TTL window are candidate hits.

### Topic Classification

Classification runs inline before the cache lookup, using a small fast model. The cost of one LLM classification call (50-100ms) is negligible against the cost of a cache miss (300-800ms for a web API call):

```python
CLASSIFY_PROMPT = """Classify this search query into one of four categories:
- breaking_news: about current events, recent releases, today's news
- research: about ML/AI techniques, papers, methods, experiments
- reference: about syntax, APIs, documentation, how-to procedures
- evergreen: about mathematical concepts, foundational theory, definitions

Query: {query}
Return only the category name."""

def classify_query(query: str) -> str:
    response = llm(CLASSIFY_PROMPT.format(query=query))
    return response.strip().lower()
```

Classification happens before embedding so that the `topic_tag` value is available both for the Qdrant filter (at read time) and for the payload write (at write time on a cache miss).

### TTL Tiers

Four topic categories with empirically reasonable defaults:

| `topic_tag`     | Example queries                                          | TTL (seconds)  |
|-----------------|----------------------------------------------------------|----------------|
| `breaking_news` | "latest GPT-5 release", "today's AI funding round"      | 3,600 (1h)     |
| `research`      | "attention mechanism transformers", "LoRA fine-tuning"  | 259,200 (72h)  |
| `reference`     | "Python list comprehension syntax", "HTTP status codes" | 604,800 (168h) |
| `evergreen`     | "backpropagation derivation", "Bayes theorem proof"     | 2,592,000 (30d)|

```python
TTL_BY_TOPIC: dict[str, int] = {
    "breaking_news": 3_600,
    "research":      259_200,
    "reference":     604_800,
    "evergreen":     2_592_000,
}

MAX_TTL = max(TTL_BY_TOPIC.values())  # 30 days: the Qdrant pre-filter window
```

The `ttl` field in the payload is set to `TTL_BY_TOPIC[topic_tag]` at write time. At read time, `created_at + ttl < now` signals that this specific entry is stale under its category's TTL, even if it passes the global `created_at` range filter.

### The 0.92 Cosine Threshold

A cache hit fires when the nearest-neighbor cosine similarity score exceeds 0.92. This is the single most consequential parameter in the web search path.

Cosine similarity between two embeddings $\mathbf{u}$ and $\mathbf{v}$ is:

$$\text{sim}(\mathbf{u}, \mathbf{v}) = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\| \|\mathbf{v}\|}$$

For research agent query distributions, 0.92 sits at the knee of the precision-recall curve for semantic equivalence. Below 0.90, the cache begins returning results for queries that share vocabulary but ask different questions. Above 0.95, the cache rarely fires on genuinely equivalent queries phrased differently.

The correct calibration procedure:
1. Log 200-400 query pairs from real agent sessions.
2. Have a human label each pair as "same intent" or "different intent."
3. Compute cosine similarity for each pair using the production embedding model.
4. Plot precision and recall at thresholds from 0.85 to 0.99.
5. Choose the threshold at the desired precision operating point.

At 0.92, I observe approximately 0.91 precision on research-domain queries: about 9% of cache hits return a result the user would consider different from a fresh fetch. Whether that rate is acceptable depends on the use case. For a drafting assistant, it usually is. For a fact-checking tool, it is not.

### Qdrant Search with Topic Filter

The web search lookup passes three filter conditions to Qdrant: `topic_tag` must match the classified topic, the entry must not be stale, and `created_at` must fall within the global maximum TTL window. The per-category TTL check is a second pass in Python:

```python
from qdrant_client import QdrantClient
from qdrant_client.models import (
    Filter, FieldCondition, Range, MatchValue
)
import time

def web_cache_lookup(query: str, topic_tag: str) -> object | None:
    query_emb = embed(query)
    now = int(time.time())

    # Step 1: ANN search with payload filter on topic_tag and freshness window
    results = client.search(
        collection_name="query_cache",
        query_vector=("query_embedding", query_emb),
        query_filter=Filter(
            must=[
                FieldCondition(
                    key="topic_tag",
                    match=MatchValue(value=topic_tag),
                ),
                FieldCondition(
                    key="stale",
                    match=MatchValue(value=False),
                ),
                FieldCondition(
                    key="created_at",
                    range=Range(gte=now - MAX_TTL),
                ),
            ]
        ),
        score_threshold=0.92,
        limit=1,
        with_payload=True,
    )

    if not results:
        return None

    hit = results[0]

    # Step 2: per-category TTL check using the stored ttl field
    if hit.payload["created_at"] + hit.payload["ttl"] < now:
        client.set_payload(
            collection_name="query_cache",
            payload={"stale": True},
            points=[hit.id],
        )
        return None

    # Update access metadata
    client.set_payload(
        collection_name="query_cache",
        payload={
            "hit_count":     hit.payload["hit_count"] + 1,
            "last_accessed": now,
        },
        points=[hit.id],
    )
    return load_result(hit.payload["result_pointer"])
```

The two-pass TTL check is by design. The Qdrant filter on `created_at >= now - MAX_TTL` pre-filters points that are clearly expired regardless of topic, using the indexed `created_at` field for an efficient range scan. The Python layer then applies the per-category TTL stored in the `ttl` payload field. This avoids pushing per-category TTL logic into the Qdrant filter expression (which would require a computed field or per-entry filter arithmetic) while still letting HNSW skip the bulk of expired entries before ANN scoring.

The filter on `topic_tag` is not just an optimization; it enforces semantic correctness. A query classified as `research` should not receive a cache hit from a `breaking_news` entry, even if the embeddings are close. A `breaking_news` entry may be several hours old and stale by `breaking_news` standards, yet still within the 30-day global window. Without the `topic_tag` filter, it would pass the `created_at` range check and potentially reach the threshold check, returning a stale result for a `research` query.

## SQL Caching: Table-Dependency Invalidation

SQL caching has a harder invalidation problem. The underlying data changes, and any cached query that touches the changed table may now return wrong results. Most SQL cache implementations respond to this by flushing the entire cache on any write, which defeats the purpose for high-write workloads.

The Qdrant architecture enables surgical invalidation: when table `orders` receives a write, only cache entries with `"orders"` in `tables_touched` are marked stale. Entries for other tables are unaffected. The `tables_touched` payload field is a keyword array; Qdrant's filter matches any point whose array contains the target value.

### Query Normalization

Before embedding a SQL query, normalize it to collapse semantically equivalent forms:

```python
import sqlparse
import re

def normalize_sql(query: str) -> str:
    parsed = sqlparse.format(
        query,
        reindent=False,
        keyword_case="lower",
        strip_comments=True,
    )
    # Replace string literals and numeric literals with placeholders
    parsed = re.sub(r"'[^']*'", "?", parsed)
    parsed = re.sub(r"\b\d+\b",  "?", parsed)
    return " ".join(parsed.split())
```

After normalization, the two example queries from the introduction become:

```
select region, sum(revenue) from orders where quarter = ? group by region
select territory as region, sum(sales_amount) as revenue from transactions where fiscal_quarter = ? group by territory
```

These are still distinct strings (different aliases, different table names), so they will not produce identical cache keys via string matching. But their embeddings will be close, and if the similarity exceeds 0.97 and the table analysis confirms equivalence, the cache returns a hit. Normalization primarily collapses queries that differ only in literal values; it does not solve the semantic equivalence problem for queries with structural differences.

The normalized SQL is embedded using a code-aware embedding model. Standard text embeddings work acceptably for SQL, but models fine-tuned on code produce meaningfully better similarity scores. `nomic-ai/nomic-embed-code` and `microsoft/codebert-base` give roughly 4-6% better recall at equivalent precision thresholds on SQL equivalence classification tasks.

### Extracting tables_touched

Table dependencies are extracted at cache-write time using `sqlparse`:

```python
import sqlparse
from sqlparse.sql import Identifier, IdentifierList
from sqlparse.tokens import Keyword, DML

def extract_tables_touched(query: str) -> list[str]:
    tables = []
    parsed = sqlparse.parse(query)[0]
    from_seen = False
    for token in parsed.tokens:
        if token.ttype is DML and token.value.lower() == "select":
            continue
        if token.ttype is Keyword and token.value.lower() in ("from", "join"):
            from_seen = True
            continue
        if from_seen:
            if isinstance(token, Identifier):
                tables.append(token.get_real_name())
            elif isinstance(token, IdentifierList):
                for identifier in token.get_identifiers():
                    if isinstance(identifier, Identifier):
                        tables.append(identifier.get_real_name())
            from_seen = False
    return [t for t in tables if t]
```

For queries with CTEs, nested subqueries, or view definitions, `sqlparse` is unreliable. A proper SQL parser (`pglast` for PostgreSQL, `sqlglot` for cross-dialect support) is more accurate. `sqlglot` handles CTEs cleanly and can resolve view definitions against a provided catalog, which matters for correctly identifying the base tables a view-referencing query actually touches.

The extracted table list is written into the `tables_touched` payload field at cache-write time. Qdrant treats this field as a keyword array: any individual value in the array can be matched by a filter condition. This is the mechanism that makes per-table invalidation O(matches) rather than O(collection size).

### Surgical Invalidation via Payload Filter

When a CDC event fires for table `orders`:

```python
from qdrant_client.models import Filter, FieldCondition, Range, MatchValue
import time

def invalidate_by_table(table_name: str):
    """Called by CDC consumer on any write to table_name."""
    offset = None

    while True:
        hits, next_offset = client.scroll(
            collection_name="query_cache",
            scroll_filter=Filter(
                must=[
                    FieldCondition(
                        key="tables_touched",
                        match=MatchValue(value=table_name),
                    ),
                    FieldCondition(
                        key="stale",
                        match=MatchValue(value=False),
                    ),
                ]
            ),
            limit=500,
            offset=offset,
            with_payload=False,
        )

        if not hits:
            break

        point_ids = [hit.id for hit in hits]
        client.set_payload(
            collection_name="query_cache",
            payload={"stale": True},
            points=point_ids,
        )

        if next_offset is None:
            break
        offset = next_offset
```

The `tables_touched` filter matches any point whose array contains `table_name` as an element, not points where `tables_touched` equals `[table_name]` exactly. A point with `tables_touched: ["orders", "regions"]` is invalidated by a write to `orders` alone. This is correct semantics: any dependency on the changed table makes the cached result potentially stale, regardless of what other tables the query also reads.

Entries are marked stale rather than immediately deleted. Stale entries are excluded from all lookups by the `stale: False` filter condition, but retained for analytics: tracking which tables appear most often in `tables_touched` for invalidated entries surfaces write-hot tables. If `orders` invalidates 60% of your SQL cache on a typical day, this signals either that `orders` receives very high write volume, or that too many queries touch it unnecessarily. Both are actionable findings for database optimization or cache warming prioritization.

A background job hard-deletes stale entries older than seven days:

```python
def purge_stale_entries(max_age_seconds: int = 604_800):
    cutoff = int(time.time()) - max_age_seconds
    client.delete(
        collection_name="query_cache",
        points_selector=Filter(
            must=[
                FieldCondition(key="stale",      match=MatchValue(value=True)),
                FieldCondition(key="created_at", range=Range(lte=cutoff)),
            ]
        ),
    )
```

### The SQL Threshold Problem

The cache hit threshold for SQL requires more care than for web search. A hit should fire only when two queries are semantically equivalent: they would return the same result set against the same database state.

Empirically, the cosine similarity distribution for SQL queries shows a useful bimodal structure. Queries that are genuinely semantically equivalent (differing only in formatting, alias names, or placeholder literals after normalization) cluster around 0.97-0.99. Queries that are similar but not equivalent (same domain and table, different filters) cluster around 0.85-0.92. The gap between 0.92 and 0.97 makes threshold selection tractable.

I use 0.97 as the default SQL threshold, versus 0.92 for web search. Any hit scoring below 0.99 triggers a secondary verification step: a lightweight query plan comparison confirms that the normalized execution paths match before the cached result is returned. This secondary check encodes the asymmetric cost of false positives: a false positive on a web search returns a slightly irrelevant document; a false positive on SQL returns wrong numbers.

For production SQL caches serving financial or medical data, the execution-plan verification step is not optional. For internal analytics dashboards with lower stakes, the 0.97 threshold alone is usually sufficient.

### Hybrid Search via Named Vectors

For the SQL path, the collection can be extended with a second named vector for SQL-specific embeddings. Adding vectors to an existing named-vector collection does not require migration:

```python
from qdrant_client.models import VectorParams, Distance

client.update_collection(
    collection_name="query_cache",
    vectors_config={
        "sql_embedding": VectorParams(size=768, distance=Distance.COSINE),
    },
)
```

The SQL cache lookup then uses Qdrant's prefetch-and-fuse hybrid search, combining `query_embedding` (for natural language intent) and `sql_embedding` (for structural equivalence), fused with Reciprocal Rank Fusion:

```python
from qdrant_client.models import (
    Prefetch, FusionQuery, Fusion, NamedVector, Filter, FieldCondition, MatchValue
)

SQL_THRESHOLD = 0.97

def sql_cache_lookup(nl_query: str, sql_query: str) -> object | None:
    nl_emb  = embed(nl_query)
    sql_emb = embed_code(normalize_sql(sql_query))

    results = client.query_points(
        collection_name="query_cache",
        prefetch=[
            Prefetch(
                query=NamedVector(name="query_embedding", vector=nl_emb),
                limit=20,
            ),
            Prefetch(
                query=NamedVector(name="sql_embedding", vector=sql_emb),
                limit=20,
            ),
        ],
        query=FusionQuery(fusion=Fusion.RRF),
        query_filter=Filter(
            must=[
                FieldCondition(key="stale", match=MatchValue(value=False)),
            ]
        ),
        limit=1,
        with_payload=True,
    )

    if not results or results[0].score < SQL_THRESHOLD:
        return None

    return load_result(results[0].payload["result_pointer"])
```

A query that scores highly on `query_embedding` (similar intent) but low on `sql_embedding` (structurally different) is probably a paraphrase that would return different data: treat as a miss. A query that scores highly on both is a strong equivalence candidate. RRF rewards consistent high ranking across both dimensions and penalizes queries that are only superficially similar in one of them.

## Frequency-Based Pre-Warming

The `hit_count` and `last_accessed` payload fields enable pre-warming for high-frequency queries. For SQL, a nightly job identifies cache entries accessed frequently within the last 24 hours, then re-executes them against the live database to refresh the result before the next request:

```python
import hashlib

def prewarm_hot_sql_queries(min_hit_count: int = 50):
    now = int(time.time())

    hot_entries, _ = client.scroll(
        collection_name="query_cache",
        scroll_filter=Filter(
            must=[
                FieldCondition(key="stale",        match=MatchValue(value=False)),
                FieldCondition(key="hit_count",    range=Range(gte=min_hit_count)),
                FieldCondition(
                    key="last_accessed",
                    range=Range(gte=now - 86_400),
                ),
            ]
        ),
        with_payload=True,
        limit=500,
    )

    for entry in hot_entries:
        fresh_result = execute_query(entry.payload["query_text"])
        fresh_hash = hashlib.sha256(serialize(fresh_result).encode()).hexdigest()

        if fresh_hash == entry.payload["result_hash"]:
            # Data unchanged: extend TTL by refreshing created_at
            client.set_payload(
                collection_name="query_cache",
                payload={"created_at": now},
                points=[entry.id],
            )
        else:
            # Data changed: update result and hash
            new_pointer = store_result(fresh_result)
            client.set_payload(
                collection_name="query_cache",
                payload={
                    "result_pointer": new_pointer,
                    "result_hash":    fresh_hash,
                    "created_at":     now,
                    "stale":          False,
                },
                points=[entry.id],
            )
```

The `result_hash` comparison is the optimization that makes pre-warming cheap for stable data. If the underlying data has not changed since the last cache write, only `created_at` is updated (effectively extending the TTL) without writing a new result to storage. For BI dashboards where the same ten queries run for hundreds of users every morning, pre-warming at 3am means every user hits a warm cache rather than triggering a cold database read.

## Measuring Cache Effectiveness

Three metrics matter:

**Hit rate.** The fraction of queries served from cache. For a research agent making 30-50 web searches per session on overlapping topics, I observe 35-45% hit rate after the first few sessions of warmup. SQL hit rate depends heavily on workload: dashboards with fixed query patterns see 70-80%; ad-hoc analytics see 10-20%.

**Precision.** The fraction of cache hits that return a result the user would have accepted if fetched fresh. For web search at cosine threshold 0.92, precision is approximately 0.91 on research-domain queries. For SQL at cosine threshold 0.97, precision exceeds 0.98 on normalized, well-structured queries. Precision degrades for queries with complex CTEs or dynamic date ranges that partially evade normalization.

**Latency savings.** A Qdrant lookup (including embedding the query) takes 10-20ms. A web search API call takes 300-800ms. A cold SQL query against a large table takes 500ms to 30 seconds. The cache is economically justified even at 10% hit rate for slow SQL queries.

Effective latency:

$$\text{Effective latency} = (1 - h) \cdot t_{\text{source}} + h \cdot t_{\text{cache}}$$

where $h$ is the hit rate, $t_{\text{source}}$ is the average source latency, and $t_{\text{cache}}$ is the Qdrant lookup latency. At $h = 0.35$, $t_{\text{source}} = 500\text{ms}$, $t_{\text{cache}} = 15\text{ms}$, effective latency drops from 500ms to 330ms: a 34% reduction even at modest hit rates.

A less obvious but useful metric: **invalidation frequency by table**, computed by counting `tables_touched` values across all invalidated entries. If `orders` appears in 60% of invalidated SQL cache entries on a typical day, it either receives very high write volume or is touched unnecessarily by many queries. Both are actionable for database optimization or pre-warming schedule adjustment.

## Challenges

**Threshold calibration is workload-specific.** The 0.92 (web) and 0.97 (SQL) thresholds I cite come from research agent and BI dashboard workloads. A customer support agent with highly specific product queries, or a code-generation agent whose SQL tends to cluster at 0.95 for semantically different queries, will need different calibration. There is no universal threshold. The cost of miscalibration is asymmetric: too low produces wrong answers (SQL) or irrelevant results (web); too high produces a cache that rarely fires. Domain-specific calibration on logged query pairs is unavoidable.

**SQL normalization is not a solved problem.** Queries that express the same computation using different views, aliases, or CTEs normalize to different strings and produce embeddings that are similar but not identical. Full semantic equivalence checking requires comparing query plans, not just strings or embeddings. For production systems serving financial or medical data, the execution-plan verification step is not optional, and it adds latency that partially offsets the cache savings.

**Cache poisoning.** A buggy agent can write incorrect results into the cache, which are then served to subsequent queries. The `result_hash` field helps detect when a pre-warmed entry's content has changed, but does not prevent incorrect computation at original write time. For SQL caching of financial data, restricting cache writes to trusted query paths and adding a result validation step before writing (sanity-checking row counts and column types against the schema) are appropriate mitigations.

**The freshness-hit-rate tradeoff has no clean solution.** Shorter TTLs improve freshness but reduce hit rate. Longer TTLs improve hit rate but surface stale results. Topic-aware TTL is a heuristic that works well on average but breaks for individual queries that do not fit neatly into a category. A learned TTL, using historical invalidation rates per query cluster to set per-cluster TTLs, would be more precise but requires significant instrumentation and a feedback loop from user corrections.

**Multi-tenant isolation.** When the cache serves multiple users or projects, query histories must not leak across tenants. Adding `tenant_id` to every payload filter is straightforward. More subtle: `result_pointer` must point to tenant-scoped storage. A misconfigured result pointer that serves one tenant's financial data to another is a security issue that payload filtering alone cannot prevent. The cache infrastructure needs explicit tenant isolation testing, including adversarial probes that attempt cross-tenant cache hits.

**Embedding model drift.** If the embedding model is updated, old embeddings in the collection are no longer comparable to new embeddings on the same scale. Cache entries written before the model update will score at incorrect similarity values against new queries. The practical mitigation options are: re-embed all collection entries on model update (expensive but complete), version the collection name and route new queries to the new version (leaving the old collection to expire naturally), or apply a calibration offset to the threshold during the transition period. None of these options is free.
